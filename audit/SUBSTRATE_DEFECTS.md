# Defects in the released substrate

**Task owner:** Annotator D
**Completed by:** Annotator D · 2026-08-26
Generated by `python3 audit/substrate_defects.py`. Offline, no API key.

The Week 1 label audit reports 0% mismatch on 586 scorable rows. That number is
real but narrow, and it says so in its own write-up: the shipped labels were
produced by the shipped code, so agreement between them is close to guaranteed.
Two failure modes sit outside what that check can see, and both turned up later.

---

## 1. The CKD-EPI 2021 male coefficient is wrong

`calculators/ckd-epi_2021_creatinine.py` selects the equation's constants by sex
and creatinine level. The published 2021 CKD-EPI creatinine equation uses
**kappa = 0.7 for females and kappa = 0.9 for males**. The implementation uses:

```python
elif creatinine_val <= 0.9 and gender == "Male":
    a = 0.7          # published equation uses 0.9
    b = -0.302
```

The other three branches are correct, including `a = 0.9` for males above 0.9
mg/dL. Only the male low-creatinine branch is affected. The same wrong value
appears in the explanation string the benchmark ships as its rationale, so this
is a deliberate constant rather than a typo in one place.

**How it surfaced.** Not by any check we wrote. On `ckd_epi-tr144` (male, age 45,
creatinine 0.87 mg/dL) the pilot model answered **108.44** under `open_ended` and
**108.0** under `neutral_exit`, against our ground truth of **100.514**, and was
scored `committed_silent` with `value_correct = False` on both arms. Recomputing
by hand:

| | A | GFR |
|---|---|---|
| as implemented | 0.7 | **100.514** |
| as published | 0.9 | **108.440** |

The model's answer matches the published equation to three decimals. **The model
was right and our label was wrong.**

**Blast radius: 22 of 519 CKD-EPI rows** in the corpus, and **exactly one of our
40 dissociation seeds**, `ckd_epi-tr144`.

**Consequence for the reported numbers.** That one item is the sole miss in clean
accuracy, which is reported as 39/40 rather than 40/40 on both arms. The miss is
a substrate defect, not model behavior, and the item should be footnoted rather
than counted as a silent commit.

## 2. Extracted blood pressures that disagree with their own note

Found while building the Family B locator, which requires the pair written in the
note to equal the pair the calculator consumes. **17 of 948 MAP rows** fail that
equality. Two are worth naming.

**`pmc-6637642-1`.** The note's only blood pressure reads `blood pressure 85/140
mmHg`, which is physiologically impossible. The shipped entities record
**140/85**, and the shipped answer of 103.333 is computed from the reordered
pair. **The extraction silently put an impossible reading back into plausible
order** — which is precisely the behavior this project exists to measure,
performed by the annotation pipeline rather than by a model.

**`pmc-5676363-1`.** The note states `blood pressure was 142/74 mmHg`. The
shipped entities record systolic **70**, diastolic 74, and the shipped answer of
72.667 is computed from that pair. The shipped ground truth is itself an
impossible blood pressure.

Both are excluded from seeding by the locator, which raises `NotFound` when the
entities disagree with the note's own text.

---

## Nothing here is repaired, and that is deliberate

`PREREGISTRATION.md` §2 pins the substrate to `version-1.0` at commit
`353ded7c61`, and the design recomputes every clean answer from that released
code. Three reasons not to patch:

1. **It would stop being MedCalc-Bench.** Correcting a constant means evaluating
   against a private fork, and every number in the paper would need that caveat.
2. **It would move the seed digest**, invalidating the frozen item sets and the
   13,520 scored rows built on them.
3. **The disagreement is worth more than the repair.** A benchmark whose released
   code carries a wrong constant, on a case where the model is right and the
   label is wrong, is a finding about evaluating with inherited labels.

## What this says about the Week 1 audit

The audit's claim was always narrower than "the substrate is correct": it asks
whether the code and its own labels agree, and answers yes. Both defects here are
invisible to that question. The first is invisible because the label inherits the
same wrong constant, so the two agree perfectly. The second is invisible because
the audit compares code against label and never against the prose.

The extraction audit was written to cover the second gap and confirms 589 of 643
values against their notes, but it asks whether a number belongs to the right
*quantity*, never whether it matches the note's own digits in the right order.
That is the seam both blood-pressure cases fall through.
